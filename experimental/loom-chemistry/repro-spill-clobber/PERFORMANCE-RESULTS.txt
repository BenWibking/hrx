Loom versus native HIP: MI300X performance investigation (2026-10-01)
===================================================================

Finding
-------
The approximately 7x full-collapse kernel-time gap persists with identical
input states, timesteps, and solver work. It is a generated-code efficiency
problem: much more memory traffic, ALU work, and branch execution. The source
rewrite is not responsible for the observed slowdown in the matched replay:
HIP compiles the rewritten source to a faster kernel than the original HIP
reference. Measurements do not yet assign an exact time fraction to spilling
versus control flow, or isolate a particular compiler commit as the cause.

The earlier accepted numerical validation remains a PASS. This investigation
changes no production compiler code, chemistry source, or numerical tolerance.

Controlled replay
-----------------
Hardware: authorized DigitalOcean MI300X droplet 134.199.200.72, gfx942.
Original GPU artifacts: af901efb55 chemistry checkout plus strict sqrt and
explicit loop SSA preservation changes, with corrected perturb argument ABI.
The local working checkout is now 907813bd6505a2b8c964f5e8e64c97bc32bcbfa4;
measurements use the preserved remote artifacts, not a new build of that HEAD.

Each advance replay loads the HIP snapshot immediately after prepare, and
uses that step's saved global dt/time. Before every sample, both backends are
reset to the same state. Only the kernel is HIP-event timed; state copies,
reset, and counter readback are outside the timed interval. One warmup per
backend is discarded, followed by five measurements with alternating order.
The native HIP kernel .text SHA256 is identical in the original full driver
and replay driver. All selected cases return SUCCESS, with exactly matching
integrated counts, internal steps, RHS calls, and Jacobian counts.

Advance medians, milliseconds (128 cells, one 128-thread block):
  saved step       native HIP       Loom       Loom/HIP
       0             6.65095       40.47708        6.09
     100             4.83359       30.97542        6.41
     500             4.67930       30.33555        6.48
     920            46.66722      314.80295        6.75
     999             5.16825       34.47662        6.67

At step 500, both integrate 127 cells and perform 134 internal steps,
402 RHS calls, and 131 Jacobian evaluations. At step 920, both integrate
126 cells with 218 internal steps, 654 RHS calls, and 164 Jacobians.

Replicating the step-500 input across 64 independent blocks (8,192 cells)
gives 5.00648 ms HIP versus 32.55440 ms Loom, a 6.50x ratio. This is a
synthetic replicated advance workload, not a larger independently initialized
collapse. It rules out the single-block launch as the sole source of the gap;
it is not a full occupancy or saturation study.

The original full-run totals were 12.44314 s HIP versus 87.29416 s Loom for
prepare plus advance. Nearly all time is advance (12.43532 s versus 87.12993 s).
Total internal steps differ by just 146 out of 220,370 (0.0663%); that cannot
account for the time ratio. The perturbing prepare replay at step 500 is also
slower, 0.010183 ms versus 0.103235 ms (seven timed samples), but prepare is
less than 0.2% of total Loom kernel time in the full run.

Code-object evidence
--------------------
Advance metadata: HIP private segment 7,504 bytes/thread, Loom 51,968.
Metadata VGPR counts: HIP 128, Loom 256. rocprof reports Loom's allocation as
128 regular plus 128 accumulator registers. These facts alone are not an
occupancy measurement. HIP SGPR metadata is 108 versus Loom 102; profiler
allocation counts round both to 112.

Static disassembly counts, advance only:
                                    native HIP         Loom
  total instructions                    70,889        364,734
  scratch loads                          3,969         24,071
  scratch stores                         1,796          8,914
  s_waitcnt                              3,506         28,561
  unconditional s_branch                    19         40,987

Static counts are not dynamic traffic. HIP scratch includes private array
accesses as well as spills. Current Loom uses private storage; older notes
about a global ScratchRecord buffer do not describe these artifacts.

Concrete inefficiencies visible in Loom's current ISA:
- Spill transfers repeatedly save EXEC, set EXEC=-1, materialize an address,
  transfer a value, and restore EXEC. SGPR backing adds vector transfers and
  v_readfirstlane. The full-value semantics must be preserved in any fix.
- A short sequence in advance stores to scratch offset 0x4d70 at PC 0x1bfc,
  reloads it at 0x1c1c and 0x1c38, then again at 0x1c7c for one division
  sequence. Nearby constant halves are themselves stored/reloaded. This is
  direct evidence of missed constant rematerialization and/or reload reuse,
  not merely a high aggregate scratch allocation.
- The binary has 10,694 unconditional branches whose immediate target is
  another unconditional branch. Branch-island relaxation is implemented in
  loom/src/loom/target/emit/native/amdgpu/branch_layout.c; large functions and
  distant merge blocks amplify the cost of an already branch-heavy lowering.
  This count includes branch chains; it does not assign all such branches
  to one producer or measure their separate runtime cost.
- Even the small prepare kernel has 337 unconditional branches versus HIP's
  one, despite only ten static scratch instructions versus HIP's zero.
  Thus spill traffic alone is not a sufficient account of all inefficiency.

Source-rewrite control
----------------------
A diagnostic-only copy of reproducer.cpp and integrate.inc was compiled by
native HIP, retaining the rewritten arithmetic. support.h was adapted only
for HIP host/device declarations, thread indexing, and HIP device atomics.
No production files were changed. Both builds use:
  hipcc -std=c++20 -O3 --offload-arch=gfx942

Step 500, five samples with alternating Loom/HIP-rewritten order:
  HIP-rewritten median 3.19394 ms; Loom median 30.41337 ms (9.52x).
The rewritten output versus saved native HIP output passes the reference
non-deuterium/thermodynamic checks; all counters match exactly. Max temperature
relative error is 4.12e-16, energy 1.81e-16, and density is exact. This control
validates this replay, not another full-collapse run.

HIP-rewritten private segment is 8,064 bytes/thread. Its dynamic VMEM count
is 56,633, VALU 358,775, and SALU 91,755. The rewritten source demonstrably
does not require Loom's machine-code expansion on this input.

Suggested next compiler experiments
----------------------------------
1. Test rematerialization of cheap constants and reuse of reloads within a
   block. Inspect spill fragmentation and avoid repeated backing transfers
   for values already available in registers. Preserve full-lane spill
   semantics and the explicit SSA loop fix.
2. Coalesce compatible full-EXEC spill regions and improve address/wait
   handling with dependency proofs. Do not simply remove waits or narrow
   EXEC: correctness constraints established by the clobbering tests remain.
3. Improve if-conversion for pure, safe expressions and place branch/merge
   blocks together before branch relaxation. Preserve lazy evaluation for
   expressions that cannot safely be speculated. Measure resulting branch
   counts, code size, pressure, and spills together.

These are experiments to isolate and reduce the costs, not validated fixes.
In particular, no before/after ablation establishes how much overhead the
recent loop-preservation change itself adds.
